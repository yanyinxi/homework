## 五、数据导入情况（三份全部导入）

| 数据集 | XLS 行数 | 有效导入 | 跳过原因 |
|--------|----------|----------|----------|
| 数据集1 | 25 | 25 | 无跳过 |
| 数据集2 | 27 | 25 | 2 条 source_id 重复（ON CONFLICT DO UPDATE 合并） |
| 数据集3 | 22 | 19 | 3 条脏数据（title 为空字符串，DB NOT NULL 约束拒绝） |
| **合计** | **74** | **69** | |

> 数据集2 重复说明：XLS 中 `asset_006`、`asset_016` 各出现 2 次；ETL 使用 `ON CONFLICT(source_dataset, source_id) DO UPDATE`，第二次入库时覆盖更新同一行，DB 最终 25 条不重复记录，行为符合预期。
>
> 数据集3 跳过说明：vid0008/vid0015/vid0017 的 `素材title` 字段在源数据中为空，ETL 归一化后为 null，被必填字段校验拦截（NOT NULL 约束要求 title 非空）。ETL 在批次写入前做行级校验，避免整批事务回滚。

## 七、ETL 修复记录

| 问题 | 根因 | 修复方案 |
|------|------|----------|
| Dataset3 导入 0 条（整批回滚） | `素材title` 为空的行被加入批次 → NOT NULL 约束导致整个事务回滚 | IngestRunner 增加行级必填字段校验，null title/uploader/status 行在归一化阶段即被跳过 |
| `"Reject"` 状态归一化失败 | STATUS_MAPPING 只有精确大小写枚举，未覆盖 "Reject" 变体 | 改为两阶段查找：精确匹配→不区分大小写英文匹配，同时在 MAP 中增加 "reject" → "rejected" |
| docker-compose 需手动 exec 导入 | IngestRunner 只在 `--ingest` 参数存在时执行 | docker-compose backend 服务追加 `command: ["--ingest=all"]`，一键启动即完成导入 |
